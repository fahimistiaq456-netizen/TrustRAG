# Multi-Domain Benchmarking

## What it does
Extends the original single-corpus (university handbook) evaluation into an independent
multi-domain benchmark so HalluFix's contribution can be measured across different
knowledge areas.

```
evaluation/
├── datasets/
│   ├── university/   documents/ + questions.json + metadata.json
│   ├── healthcare/
│   ├── technology/
│   ├── law/
│   └── finance/
├── results/           results.json (machine-readable) + report.md
├── evaluate.py        CLI runner
├── metrics.py         pure metric helpers
├── make_datasets.py   regenerates the synthetic datasets
```

## Why it exists
A single handbook cannot show that RAG, reranking and NLI generalise. Distinct domains
let the thesis report recall/precision/MRR, answer correctness, abstention behaviour and
unsupported-claim rates per domain — and compare configurations head-to-head.

## Question types
Each `questions.json` entry uses `expected_type` (also accepts `category`):
`answerable`, `unanswerable`, `misleading`, `contradiction`, `multi-hop`. Example:

```json
{
  "id": "uni-001",
  "domain": "university",
  "question": "How many credits are required to graduate?",
  "expected_type": "answerable",
  "reference_answer": "120 credits",
  "expected_sources": ["academic_policy.md"]
}
```

## Runner + metrics
```bash
python -m evaluation.evaluate --domain university   # one domain
python -m evaluation.evaluate --all                 # every domain
python -m evaluation.evaluate --list                # available datasets
python -m evaluation.evaluate --offline --all       # no API calls (metrics = N/A)
```
Per question, `evaluate_question` computes:
- **Retrieval**: `recall@5`, `precision@5`, `mrr` against `expected_sources`.
- **Hallucination control**: `abstention_accurate`, `unsupported_claims`.
- **Answer quality**: `answer_correct` (token-overlap grounding against `reference_answer`).
- **Verification**: implied by supported/unsupported claim counts.

`metrics.aggregate` rolls these up per domain and for `all`, writing
`evaluation/results/results.json` (JSON) and `evaluation/results/report.md` (Markdown). When
a live field was not computable (e.g. an offline run) it is reported as `N/A` rather than
fabricated — a reproducibility requirement of the project.

## Comparing configurations
Run the suite through the live `/ask` endpoint and note each configuration's
`config.py`/`.env` state in the report header:
- baseline RAG (reranker + NLI + graph disabled)
- RAG + reranking
- RAG + reranking + NLI
- full Hallufix (graph on as well, when relevant)

Because the API runs a single pipeline, reproduce a given configuration by toggling the
relevant `HALLUFIX_*` env vars and re-running `python -m evaluation.evaluate --all`.

## Datasets & licensing
Datasets are **synthetic** (generated by `evaluation/make_datasets.py`) or built from
clearly licensed/public-domain-style material — no copyrighted documents are redistributed.
`metadata.json` records license + provenance for reproducibility.

## Testing
```bash
pytest tests/test_evaluation.py
```
Covers dataset layout (all 5 domains present), metric helpers, abstention accuracy,
multi-domain correctness, and offline (`response=None`) behaviour.
